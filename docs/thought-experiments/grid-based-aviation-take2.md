# Try again. Promise Grid is not a blockchain-based system. There is no single grid currency. The closest thing to any currency is the capability tokens that act as promises, which are issued by individual entities in the system. And act as promises granting access to resources when requests are later presented along with the capability token. There is no DAO, or other commonly hyped blockchain concepts. Please imagine original concepts rather than retreading cryptocurrencies. Also, voting is filled with pitfalls because voting systems do not directly hold the voters accountable for their decisions..

The revised report is much closer to what you were asking for. Here's a brief orientation to what changed and why:

**What was wrong before**: The first version retrofitted crypto/DAO vocabulary onto PromiseGrid's architecture. That was lazy pattern-matching — grabbing familiar "decentralized governance" buzzwords instead of reasoning from first principles about how capability tokens, merge-as-consensus, and promise theory actually work.

**What drives this version**:

- **No voting anywhere.** Instead, every consequential assertion is a capability token issued by a named, identifiable agent. The entire accountability mechanism flows from the fact that promise-keeping records are permanently written into the directed graph cache — legible to every downstream agent, forever. A bad assessor doesn't get "voted out"; they simply find that no one will extend them capability tokens worth relying on.[^1][^2]
- **Standards as WASM modules, not committees.** A design standard is a pure function — content-addressed, reproducible on any node.[^3][^4] Certification is running the function against the design package. Multiple competing standards modules can coexist; airport access policies are predicates over which modules a design has passed. No standards body has authority; influence flows only from promise-keeping record.
- **The airframe IS a promise graph.** Its serial number is the root hash of its build promise. Every build step, inspection, repair, and incident is a promise fulfillment or breaking, signed by the specific human who made it, permanently cached. There's no logbook — there's a directed acyclic graph.[^3]
- **Airspace coordination without controllers.** Flight intent is a published promise. Conflict detection is a pure function running on every node including airborne avionics. Position broadcasts are continuous promise fulfillments. Deviation from published intent is promise-breaking evidence, recorded in real time.[^2]

The accountability model in this version is grounded in what Promise Theory actually says: the only thing that enforces behavior is that every agent can read every other agent's complete promise history before deciding whether to extend capability tokens to them.[^5][^1]
