Garmin Pilot: Navlog & Checklist Integration
Garmin Pilot is designed to mimic the GTN 750/G1000 avionics workflow. It is less "form-based" than ForeFlight and more "task-based."
Integration: In Garmin Pilot, the NavLog and Checklist are separate tabs, but you can view them in "Split Screen" mode on the iPad Mini.
Frequencies/TPA: When you enter a destination airport in your flight plan, Garmin Pilot automatically populates a "Waypoints" info page. It includes TPA (Traffic Pattern Altitude), all Communication Frequencies, and runway data. You don't "import" these into the checklist; they live in the NavLog data layer and are one tap away.
CAPS/Aircraft Specifics: These are handled via Aircraft Profiles. You can customize the "Performance" and "Basic Empty Weight" files. For CAPS (Cirrus Airframe Parachute System) altitudes, you would typically add these as custom entries in the Checklist module rather than the NavLog.
The "Wizard" vs. Manual Entry:
The Wizard: Garmin uses a "Trip Planning" workflow. You enter Origin > Destination > ETD > Altitude. It calculates the NavLog (ETE, Fuel, Wind) automatically.
Customization: You can manually add "User Waypoints" (e.g., a specific visual landmark for a CAPS deployment point) and custom data fields in the NavLog view (like Groundspeed, ETA, Distance to TOD).
Developing for iOS: The "Hurdles" Roadmap
As a Go developer moving to iOS, the biggest hurdle is the walled garden. Here is the path to getting your prototype on your iPad Mini:
1. The Development Environment
The Mac Requirement: You must have a Mac running macOS to run Xcode. You cannot compile iOS apps directly from Windows or Linux.
The Language Bridge: Since you use Go, you will likely use Gomobile. You'll write your logic in Go, run gomobile bind, and it spits out a .framework file that you drag into Xcode. Your UI will be written in SwiftUI.
2. Installing on Your Own iPad (The "Free" Tier)
The Hurdle: Apple allows "Side-loading" for development, but with a catch.
The Limit: If you don't pay for a developer account, your "Provisioning Profile" (the digital permission slip) expires every 7 days. You will have to re-plug your iPad into your Mac and re-deploy the app weekly.
No App Store: You can only install it on your own physical devices via a USB cable.
3. Small Group Beta Testing (The $99/year Tier)
To let friends test it without them plugging into your Mac, you must join the Apple Developer Program ($99 USD/year).
TestFlight: This is Apple’s official beta testing platform. You upload your build to the cloud, and your friends install it via the "TestFlight" app.
Review: Even beta builds go through a "Beta App Review," though it is much less strict than the full App Store review.
4. The Full App Store Release
Human Interface Guidelines (HIG): Apple is strict about UI. If your app looks "broken" or doesn't follow standard iPad navigation patterns, they will reject it.
The "Safety" Hurdle: Since this is an aviation app, Apple may require a disclaimer stating the app is for "Situational Awareness Only" and not for primary navigation to shield themselves (and you) from liability.
Your Best "Hybrid" Path
If you want to stay in Go as much as possible:
Logic: Write the NavLog/Checklist logic in Go.
UI: Use SwiftUI. It is declarative (similar to React) and much easier for a backend/CLI developer to learn than the old UIKit.
Data: Use SQLite (Go has great support) to store your airport frequencies and CAPS data locally on the iPad.

compare garmin and foreflight's navlogs
When comparing ForeFlight and Garmin Pilot navlogs, the choice usually comes down to whether you prefer an intuitive, flexible planning workflow or a hardware-integrated, pilot-standard interface.
1. Planning Workflow & NavLog Structure
ForeFlight (The Planning King): Navlogs in ForeFlight are built around a highly flexible "Edit" box where you can type an entire route in one string. The NavLog is a dedicated tab that clearly breaks down ETE, Fuel, and Distance with a "what-if" planning style that makes it easy to quickly test different altitudes or routes.
Garmin Pilot (The Avionics Mirror): Navlogs are integrated into a "Trip Planning" workflow that mimics the interface of GTN 650/750 navigators. It is more "task-based," requiring separate entries for origin, destination, and waypoints, which some find clunky compared to ForeFlight’s one-box entry.

given an airport code, is there a publicly-accessible and authoritative database that can give me the frequencies?
For a developer, the answer depends on whether you are flying in the United States or Internationally.
1. United States (The "Gold Standard" Data)
If your flying is primarily in the US, you are in luck. The FAA provides the most authoritative data in the world for free.
The Source: The NASR (National Airspace System Resources) database.
How to access it: The FAA provides "Subscriber Files" that are updated every 28 days.
The Best API for Go Developers: Instead of parsing raw fixed-width FAA text files (which is a nightmare), use the FAA NASR API or the FAA's Aeronautical Data Portal.
What you get: Precise frequencies (Tower, Ground, CTAF, ATIS, UNICOM), Traffic Pattern Altitudes (TPA), and even the latitude/longitude of the radio antennas.
2. International (Worldwide)
Outside the US, data is often guarded by individual countries' AIPs (Aeronautical Information Publications), which are usually PDFs and hard to scrape. To get global data, you have two main options:
Option A: OurAirports (Free/Public Domain)
This is the "Wikipedia" of airport data. It is widely used by open-source flight sim projects.
Format: CSV files updated daily.
URL: OurAirports.com Data Downloads
Go Implementation: You can write a Go routine to GET the airport-frequencies.csv file and parse it into a struct. It’s very reliable for GA airports.
Option B: CheckWX API (Developer Friendly)
While primarily for METAR/TAF, they provide airport metadata including frequencies.
Format: JSON API.
URL: CheckWX API
3. Recommendation for your Web Tool
Since you are a Go programmer building a Navlog tool, I recommend the OurAirports CSV approach for your prototype because it is "zero-latency" (you can ship the data within your Go binary using embed).
Example Go Logic:
Download airports.csv and airport-frequencies.csv.
Filter by the ICAO code the user enters in your web form.
Extract the type (e.g., "TWR", "ATIS") and frequency_mhz.
4. A Note on TPA and CAPS Altitudes
TPA: This is usually not in the "frequency" tables. In the US, you find this in the Chart Supplement (formerly A/FD). Parsing this is harder because it is often hidden in text remarks (e.g., "TPA—1000(812)").
CAPS Altitudes: This is not in any public airport database. It is specific to the Cirrus POH (Pilot's Operating Handbook). You will need to hard-code these values or create your own lookup table (e.g., a Go map[string]int where the key is the aircraft model).
